# QoS Traffic Management System

## 1. Project Overview

The QoS Traffic Management System is a Computer Networks mini-project that demonstrates Quality of Service (QoS) using Software-Defined Networking (SDN).

The system classifies network traffic into three priority classes and assigns each class to a dedicated Open vSwitch (OVS) queue using OpenFlow rules controlled by a Ryu SDN controller.

The main objective is to prioritize latency-sensitive traffic such as voice over video and best-effort traffic.

## 2. Technologies Used

- Python
- Ryu SDN Controller
- Mininet
- Open vSwitch (OVS)
- OpenFlow 1.3
- UDP sockets
- Linux HTB Queueing
- CSV-based traffic logging

## 3. System Architecture

The project uses a simple Mininet topology:

```text
             Ryu Controller
                   |
             OpenFlow 1.3
                   |
                 Switch
                  s1
                /    \
               /      \
             h1        h2
          Sender     Receiver
```

Traffic is generated by the sender on h1 and transmitted through the OVS switch to the receiver on h2.

The Ryu controller classifies traffic based on UDP destination ports and installs OpenFlow rules to assign the appropriate queue.

## 4. Traffic Classification

Three traffic classes are implemented.

| Traffic class | Priority | UDP port | Queue ID | Flow priority |
|---|---|---:|---:|---:|
| Voice | HIGH | 5001 | 3 | 300 |
| Video | MEDIUM | 5002 | 2 | 200 |
| Best effort | LOW | 5003 | 1 | 100 |

### Queue bandwidth configuration

The OVS Linux HTB QoS configuration uses:

| Queue | Traffic class | Minimum rate | Maximum rate |
|---|---|---:|---:|
| 1 | Best effort | 1 Mbps | 2 Mbps |
| 2 | Video | 2 Mbps | 3 Mbps |
| 3 | Voice | 3 Mbps | 5 Mbps |

Parent bandwidth limit: 10 Mbps.

QoS is configured on the switch output port `s1-eth2` for traffic travelling from h1 to h2.

## 6. Running the Project

### Step 1: Start the Ryu controller

Activate the Python virtual environment:

```fish
cd ~/qos-project
source ryu-env/bin/activate.fish
```

Start the controller:

```fish
ryu-manager --ofp-tcp-listen-port 6653 controller/qos_controller.py
```

### Step 2: Start Mininet

Open another terminal:

```fish
sudo mn --topo single,2 --mac --switch ovsk,protocols=OpenFlow13 --controller remote,ip=127.0.0.1,port=6653
```

The topology contains:

- h1: 10.0.0.1
- h2: 10.0.0.2
- Switch: s1

### Step 3: Verify connectivity

At the Mininet prompt:

```text
pingall
```

### Step 4: Start the receiver

At the Mininet prompt:

```text
h2 python3 -u /home/vismay/qos-project/app/receiver.py --log /tmp/receiver.csv
```

### Step 5: Generate traffic

Voice:

```text
h1 python3 /home/vismay/qos-project/app/sender.py --host 10.0.0.2 --port 5001 --class-name voice --rate 50 --duration 5 --payload-size 256 --log /tmp/voice.csv
```

Video:

```text
h1 python3 /home/vismay/qos-project/app/sender.py --host 10.0.0.2 --port 5002 --class-name video --rate 30 --duration 5 --payload-size 256 --log /tmp/video.csv
```

Best effort:

```text
h1 python3 /home/vismay/qos-project/app/sender.py --host 10.0.0.2 --port 5003 --class-name best_effort --rate 20 --duration 5 --payload-size 256 --log /tmp/best_effort.csv
```

## 7. OpenFlow Verification

To inspect installed OpenFlow rules:

```text
sh ovs-ofctl -O OpenFlow13 dump-flows s1
```

Expected traffic classification:

```text
UDP destination port 5001 -> Queue 3
UDP destination port 5002 -> Queue 2
UDP destination port 5003 -> Queue 1
```

The controller installs rules using:

- HIGH: priority 300, queue 3
- MEDIUM: priority 200, queue 2
- LOW: priority 100, queue 1

## 8. QoS Verification

Check whether QoS is attached to the output port:

```text
sh ovs-vsctl list Port s1-eth2
```

Inspect QoS configuration:

```text
sh ovs-vsctl list QoS
```

Inspect queue configuration:

```text
sh ovs-vsctl list Queue
```

Inspect queue statistics:

```text
sh ovs-ofctl -O OpenFlow13 queue-stats s1
```

## 9. Experimental Results

### Test 1: Basic traffic classification

Traffic was sent at relatively low rates.

| Traffic class | Packets sent | Packets received | Packet loss |
|---|---:|---:|---:|
| Voice | 500 | 500 | 0% |
| Video | 300 | 300 | 0% |
| Best effort | 200 | 200 | 0% |

The controller successfully classified all three traffic classes.

### Test 2: Higher-load traffic test

Higher traffic rates were used to evaluate the system under increased load.

| Traffic class | Actual sending rate | Packets sent |
|---|---:|---:|
| Voice | 587.43 pps | 5926 |
| Video | 354.54 pps | 3606 |
| Best effort | 237.96 pps | 2434 |

Measured mean apparent delay:

| Traffic class | Mean apparent delay |
|---|---:|
| Voice | 92.461 ms |
| Video | 195.186 ms |
| Best effort | 294.356 ms |

All packets recorded in the receiver CSV matched the corresponding sender sequence counts.

The results showed lower apparent delay for higher-priority traffic in this experiment.

### Test 3: Live QoS integration and queue verification

This test was conducted after attaching the existing Linux HTB QoS configuration to `s1-eth2`.

Each traffic class was tested separately.

| Traffic class | UDP port | Target rate | Duration | Packets sent |
|---|---:|---:|---:|---:|
| Voice | 5001 | 50 pps | 5 seconds | 250 |
| Video | 5002 | 30 pps | 5 seconds | 150 |
| Best effort | 5003 | 20 pps | 5 seconds | 100 |

All three senders completed successfully with zero send errors.

### Test 3: OVS queue statistics

Final OVS queue statistics:

| Queue | Traffic class | Packets | Errors |
|---|---|---:|---:|
| Queue 1 | Best effort | 103 | 0 |
| Queue 2 | Video | 153 | 0 |
| Queue 3 | Voice | 253 | 0 |

The additional three packets per queue are consistent with termination/control traffic beyond the application data packets.

These results confirm that:

1. Voice traffic was assigned to Queue 3.
2. Video traffic was assigned to Queue 2.
3. Best-effort traffic was assigned to Queue 1.
4. All three queues recorded packet activity.
5. No queue errors were reported.

**Important:** Test 3 verifies traffic classification, queue assignment and OVS queue counters. It does not independently establish bandwidth guarantees or prove performance superiority under congestion. A controlled QoS-enabled versus QoS-disabled comparison is still required for that conclusion.

## 13. Conclusion

The QoS Traffic Management System demonstrates the use of SDN and OpenFlow to classify network traffic and assign different priority levels using OVS queues.

The Ryu controller successfully identifies voice, video and best-effort traffic based on UDP destination ports.

Live testing confirmed that the three traffic classes were assigned to their intended queues, and OVS queue statistics recorded packet activity without errors.

The project demonstrates the integration of Mininet, Open vSwitch, Ryu and Python socket programming for traffic-aware network management.
